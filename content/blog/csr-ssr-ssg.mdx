為了讓自己更了解前端世界，我想把值得學習的東西都記錄下來！

這篇要整理的是三種常見的網頁渲染方式：CSR、SSR 和 SSG。它們的差別說穿了只有一個問題：**HTML 是在什麼時候、在哪裡產生的？**

在進入正題之前，先認識三個會一直出現的名詞。

## 先認識三個名詞

### Client side（客戶端）

Client side 指的是執行在使用者設備上的程式，對網頁來說通常就是瀏覽器。

- 執行在使用者的設備上。
- 負責顯示介面、處理使用者的操作和驗證輸入。
- 需要資料時，向伺服器發送請求並接收回應。

### Server side（伺服器端）

Server side 指的是執行在遠端伺服器上的程式。

- 執行在遠端的伺服器上。
- 負責商業邏輯、資料處理和資料庫操作。
- 接收客戶端的請求，處理完再把結果回傳。

兩邊透過 HTTP 協定溝通。Client 是主動的一方，發出請求（request）之後等待回應；Server 是被動的一方，收到請求才開始處理，然後回傳回應（response）。

### Render（渲染）

渲染是指把 HTML、CSS 和 JavaScript 變成使用者看得到、可以操作的頁面的過程。

## 三種渲染方式的概念

- **CSR（Client-Side Rendering）客戶端渲染**：伺服器只給一個幾乎空白的 HTML 和 JavaScript，由瀏覽器執行 JavaScript 來產生頁面內容。
- **SSR（Server-Side Rendering）伺服器端渲染**：每次收到請求，伺服器都當場產生完整的 HTML 再回傳。
- **SSG（Static Site Generation）靜態網站生成**：在網站建置（build）的時候就把所有頁面的 HTML 產生好，之後有人來就直接給現成的檔案。

看到這裡，大家應該跟當時的我一樣霧煞煞～所以先用一個生活的例子來解釋。

## 用旅行來理解

假設你是一位旅行者，而你的旅遊行程就是一個網站。同一趟旅行，有三種安排方式。

### SSR：參加旅行團

你參加了旅行團，行程全部由導遊（伺服器）負責。每到一個地方，導遊都已經把景點、住宿和交通安排好，直接告訴你接下來要做什麼。你不用自己規劃，拿到的永遠是整理好的完整行程。

代價是導遊很忙：每個團員、每一站都要他親自安排。

### CSR：自助旅行加上旅遊 App

你決定自助旅行，出發前只下載了一個旅遊 App（JavaScript）。一開始你手上只有一張很簡單的行程表，沒有任何細節。想知道某個景點的介紹時，就打開 App，它會依照你的選擇當場查資料、產生內容。

出發前要先花時間把 App 下載好，但之後想看什麼都很快，也不用再麻煩任何人。

### SSG：帶一本旅遊手冊

你也是自助旅行，但出發前買了一本旅遊手冊（靜態 HTML 檔案）。所有景點的介紹、地圖和交通方式都已經印在裡面，隨時翻開就有，不用等任何人，也不需要網路。

缺點是手冊印好就不會變了。景點如果臨時休館，手冊上不會告訴你，要等下一版重印。

有了這個概念，接下來就可以好好看三者的差異和優缺點了！

## CSR（Client-Side Rendering）

CSR 表示頁面的內容是由瀏覽器端的 JavaScript 產生的。伺服器回傳的 HTML 幾乎是空的，瀏覽器要先下載並執行 JavaScript，才能把畫面畫出來。

### 優點

- **伺服器壓力小**：伺服器只需要提供靜態檔案和資料 API，不必替每個請求產生 HTML。
- **頁面切換快**：換頁時不用重新向伺服器要一整份 HTML，只需要取得新頁面的資料，再更新畫面上有變動的部分，操作起來很像原生 App。

### 缺點

- **首次載入慢**：使用者要等 JavaScript 下載、執行完才看得到內容，JavaScript 越大等越久。
- **SEO 較差**：爬蟲一開始拿到的是空白的 HTML。Google 的爬蟲雖然會執行 JavaScript，但不是每個搜尋引擎和社群平台的爬蟲都會，結果也比較不穩定。

### 使用時機

適合互動性高、內容因人而異的網頁應用程式，例如社群平台、即時通訊、協作工具，或是登入後才看得到的後台。這類產品不太需要被搜尋到，使用者也會停留很久，流暢的操作體驗比首次載入速度更重要。

如果想保留 CSR 的互動性又要解決 SEO 的問題，通常會採用 **pre-rendering**，也就是在送到 Client 端之前就先把 HTML 產生好。常見的做法有兩種，就是接下來要介紹的 SSR 和 SSG。

## SSR（Server-Side Rendering）

SSR 表示伺服器每次收到請求時，都會在伺服器端產生完整的 HTML。使用者一拿到回應，就能看到有內容的頁面。

### 優點

- **很快就能看到內容**：HTML 送到的時候內容已經在裡面，不用等 JavaScript 執行。
- **有利於 SEO**：爬蟲拿到的就是完整的頁面，可以準確抓到內容。
- **內容永遠是最新的**：每次請求都重新產生，適合資料經常變動的頁面。

### 缺點

- **伺服器壓力大**：每個請求都要產生一次 HTML，流量大的時候成本很高。（導遊壓力大啊）
- **回應時間受伺服器影響**：伺服器要先把資料查完、頁面組好才能回傳，資料查得慢，使用者就等得久。
- **傳統 SSR 的換頁體驗較差**：每次換頁都要重新載入整個頁面。（只能給導遊安排行程，哭了 🥲）

關於最後一點要補充：現在的框架（例如 Next.js）已經改善了這個問題。它們會在第一次載入時用 SSR 送出完整的 HTML，接著在瀏覽器端載入 JavaScript 接手頁面的互動，這個過程叫做 **hydration**。之後的換頁就可以像 CSR 一樣流暢。

### 使用時機

適合需要 SEO、內容又會頻繁更新或因人而異的網站，例如新聞網站、電商的商品頁、社群平台的公開頁面。

## SSG（Static Site Generation）

SSG 表示在網站建置的時候，就把所有頁面預先渲染成靜態的 HTML 檔案。使用者來訪時，伺服器不需要做任何運算，直接把檔案送出去。

### 優點

- **速度最快**：頁面都是現成的檔案，還可以放在 CDN 上，從離使用者最近的節點送出。
- **有利於 SEO**：跟 SSR 一樣，爬蟲拿到的是完整的 HTML。
- **便宜又穩定**：不需要一直運作的伺服器，流量暴增也不容易掛掉。

### 缺點

- **不適合動態內容**：HTML 在建置時就固定了，沒辦法依照每個使用者或每次請求產生不同的內容。
- **更新要重新建置**：每次內容有變動，都要重新建置並部署。頁面數量很多時，建置時間會變得很長。

針對第二個缺點，Next.js 提供了 ISR（Incremental Static Regeneration），可以在不重新建置整個網站的情況下，定期更新個別的頁面。

### 使用時機

適合內容不常變動、每個人看到都一樣的網站，例如部落格、技術文件、產品介紹頁。（你現在看的這個部落格就是。）

## 結語

這三種方式沒有哪一個最好，只有適不適合。而且現在的框架大多可以混用：同一個網站裡，部落格文章用 SSG、商品頁用 SSR、會員後台用 CSR，都是很常見的做法。

所以比起背優缺點，更重要的是每次都回到一開始的那個問題：這個頁面的 HTML，應該在什麼時候、在哪裡產生？
