為什麼我們需要前端框架？這是我第一次接觸框架（Next.js）時問自己的問題。

我覺得這個問題蠻重要的。框架用起來太順了，很容易就一路開發下去，卻說不出它到底幫我們做了什麼。這篇整理我自己的想法，也歡迎大家跟我討論～

我那時候是從一個很簡單的問題開始問起。

## 「回歸本質，什麼是 HTML？」

HTML（HyperText Markup Language）是構成網頁的基礎。它用 tag 和 attribute 描述網頁內容的結構和含義：哪一段是標題、哪一段是段落、哪裡有一顆按鈕。

問完這個，接著問下一個。

## 「瀏覽器怎麼把我寫的 HTML 變成畫面？」

瀏覽器的渲染流程可以寫成一整篇文章，這邊只抓跟主題有關的部分。

瀏覽器拿到 HTML 之後，main thread 上的 HTML parser 會把它解析成一棵 **DOM tree**。DOM tree 是瀏覽器在記憶體裡對這份文件的表示方式，每個 tag 都是樹上的一個節點。接著瀏覽器才根據這棵樹算出每個元素的位置和大小，最後畫到螢幕上。

整個流程大致是這樣：

```text
HTML -> Tokenize -> Node -> DOM tree -> Render tree -> Layout -> Paint
```

（這裡省略了 CSSOM 的部分）

重點在後半段：**只要 DOM 改變，瀏覽器就可能要重新計算版面（Reflow）和重新繪製（Repaint）**。這兩件事都有成本，改得越頻繁、影響範圍越大，網頁就越容易卡。

## 「那直接操作 DOM 有什麼問題？」

用 Vanilla JS 當然可以做出任何網頁，問題出在網頁變複雜之後。

每當資料改變，我們都要自己找出畫面上哪些地方跟這筆資料有關，再一個一個去改。功能少的時候沒什麼感覺，功能一多，就會開始出現兩種狀況：

- **漏改**：資料變了，但畫面上某個角落忘記更新，於是出現資料和畫面對不上的 bug。
- **亂改**：為了保險乾脆整塊重畫，或是在短時間內反覆修改 DOM，造成一堆不必要的 Reflow 和 Repaint。

也就是說，真正累人的是「讓畫面永遠跟資料保持一致」這件事，而效能問題通常是手動做這件事做不好的副作用。

這時候就輪到前端框架出場了。

## 「什麼是前端框架？」

常聽到的有 React、Vue、Angular，還有建立在 React 之上的 Next.js。（嚴格來說 React 自稱是 library，不過大家習慣一起討論，這篇就統稱框架。）

簡單來說，框架把那些每個專案都要重做一次的基礎工作先做好，讓開發者可以專注在產品本身。其中最核心的一件就是上面說的 DOM 更新：

**我們只要描述「資料長這樣的時候，畫面應該長怎樣」，框架會負責算出哪些 DOM 需要改，再幫我們改。**

要注意的是，框架並沒有讓 DOM 操作消失，它只是替我們做，而且做得比較有紀律。以 React 為例，它會先在記憶體裡比較更新前後的 Virtual DOM，找出真正有差異的地方，再一次更新到真實的 DOM 上。它不一定比手寫到極致的 Vanilla JS 快，但能讓一個複雜的應用在好維護的前提下，維持夠好的效能。

隨著現在的產品功能越來越多、邏輯越來越複雜，這件事的價值也越來越大。

我認為前端框架最主要的 feature 有三個，以下都以 React 為例。

### 1. Component：把畫面拆成一塊一塊

假設我們的購物網站有這些需求：

- 顯示商品列表。
- 點擊「加入購物車」後，商品會出現在購物車列表。
- 購物車的數量要即時更新。

用 Vanilla JS 寫，流程會是：監聽點擊事件、更新資料、再手動把相關的畫面都改一遍。功能越加越多之後，程式碼會變得又長又難維護，需求一改就牽一髮而動全身。

用 React 的話，我們可以把畫面拆成多個 Component，例如 `ProductList` 和 `Cart`。每個 Component 只負責自己那一塊，職責很清楚。當購物車數量改變時，只有跟它有關的 Component 需要更新，其他部分不受影響。

### 2. State：資料變了，畫面自己跟上

拿大家一定寫過的 Counter 當例子。用 Vanilla JS，我們要用變數存狀態，用 `getElementById` 找到元素，用 `addEventListener` 監聽事件，然後在每次狀態改變後記得呼叫 `render()`：

```js
let count = 0;

function render() {
  const display = document.getElementById("count-display");
  display.textContent = `Count: ${count}`;
}

document.getElementById("increment").addEventListener("click", () => {
  count++;
  render();
});

document.getElementById("decrement").addEventListener("click", () => {
  count--;
  render();
});

render();
```

換成 React，我們只要宣告一個 state，並寫出「畫面跟 state 的關係」。之後只要呼叫 `setCount`，React 就會自己更新畫面：

```jsx
import { useState } from "react";

function Counter() {
  const [count, setCount] = useState(0);

  return (
    <div>
      <h1>Count: {count}</h1>
      <button onClick={() => setCount(count + 1)}>Increment</button>
      <button onClick={() => setCount(count - 1)}>Decrement</button>
    </div>
  );
}

export default Counter;
```

兩段程式碼做的事一樣，差別在第二段裡完全沒有出現「去改 DOM」這個動作，也就不會有忘記呼叫 `render()` 的問題。

### 3. Routing：換頁不用自己刻

用 Vanilla JS 做多頁面的應用，要自己監聽網址變化、判斷現在該顯示哪個頁面，還要處理上一頁、下一頁的行為。

Next.js 和 React Router 這類工具把這些都包好了。我們只要定義好「哪個網址對應哪個頁面」，換頁和狀態保存都交給它處理。

## 用框架之前，先想三件事

讀到這裡，用過框架的人應該都會同意它真的很方便。不過在享受便利的同時，我覺得有三件事值得先想清楚。

### 真的需要框架嗎？

如果只是一個靜態頁面，或只有少量互動，框架帶來的複雜度和額外的 JavaScript 可能比它解決的問題還多。這種情況下，簡單的 HTML、CSS 加一點 JavaScript 反而更快、更好維護。

### 該選哪一個？

確定需要之後，再依照專案的性質來選：

- **內容為主的網站（如 Blog）**：適合 Next.js 或 Astro。Next.js 可以在伺服器端先把頁面渲染好，對 SEO 有幫助；Astro 則以輕量和快速產生靜態頁面聞名。
- **互動性高的應用（如即時儀表板）**：適合以 React 這類框架在瀏覽器端渲染，頁面載入後的操作會比較流暢。

### 基礎夠不夠？

用框架之前，建議先熟悉 Vanilla JS。知道框架在背後幫我們做了哪些事，上手會快很多，遇到問題時也比較不會卡在「這到底是 JavaScript 的行為，還是框架的行為」。

## 結語

回到一開始的問題：我們需要前端框架，是因為它幫我們扛下了「讓畫面跟資料保持一致」這件又繁瑣又容易出錯的工作。

想清楚這一點，就能更有目的地使用框架，也更知道什麼時候其實不需要它！
